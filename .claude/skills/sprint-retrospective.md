# 스프린트 회고 (Sprint Retrospective)

## 스킬 설명
스프린트 종료 후 팀의 협업 방식과 프로세스를 반성하고,
다음 스프린트에서 실제로 적용할 개선 액션을 도출하는 스킬이다.
What went well / What didn't / What to improve의 구조에서
데이터 기반 분석과 구체적 액션 플랜까지 포함한다.

## 사용 시점
- 스프린트 종료 후 팀 회고를 진행할 때
- 반복되는 문제의 근본 원인을 파악해야 할 때
- 팀 협업 방식과 프로세스를 개선하고 싶을 때
- 회고 결과를 이해관계자에게 보고해야 할 때

---

## 실행 지침

### Step 1: 스프린트 데이터 수집

회고 전 다음 지표를 준비한다:

**정량 지표:**
| 지표 | 목표 | 실제 | 달성률 |
|------|------|------|-------|
| 완료 스토리 포인트 | - | - | - |
| 스프린트 목표 달성 | ✅/❌ | - | - |
| 결함 발생 건수 | - | - | - |
| 계획 대비 추가/제거된 스토리 | - | - | - |

**정성 지표:**
- 팀 에너지 레벨 (1~5점, 익명 투표)
- 협업 만족도 (1~5점, 익명 투표)

### Step 2: 회고 형식 선택

상황에 맞는 회고 포맷을 선택한다:

**① 4L 회고** (일반적인 스프린트에 적합)
| 카테고리 | 질문 |
|---------|------|
| **L**iked | 좋았던 것, 유지하고 싶은 것 |
| **L**earned | 배운 것, 새롭게 알게 된 것 |
| **L**acked | 부족했던 것, 아쉬웠던 것 |
| **L**onged for | 바라는 것, 다음에 해보고 싶은 것 |

**② Start / Stop / Continue** (프로세스 변화에 적합)
| 카테고리 | 의미 |
|---------|------|
| **Start** | 앞으로 새로 시작해야 할 것 |
| **Stop** | 당장 멈춰야 할 것 |
| **Continue** | 계속 이어가야 할 것 |

**③ Mad / Sad / Glad** (팀 감정 회복에 적합)
| 카테고리 | 의미 |
|---------|------|
| **Mad** | 화나거나 불편했던 것 |
| **Sad** | 아쉽거나 실망스러웠던 것 |
| **Glad** | 기쁘거나 자랑스러웠던 것 |

**④ 5 Whys** (반복 문제 근본 원인 분석)
```
문제 현상 → Why? → Why? → Why? → Why? → Why? → 근본 원인
```

### Step 3: 의견 수집 및 그룹화

**진행 방법:**
1. 개인별 포스트잇 작성 (5분, 침묵 브레인스토밍)
2. 발표 및 보드에 붙이기 (각 1~2문장)
3. 유사 항목 그룹화 (어피니티 다이어그램)
4. 그룹별 투표 (각 3표씩 중요도 투표)
5. 상위 3~5개 주제 선정

**퍼실리테이션 원칙:**
- 특정인 비난 금지: "팀원A가 늦어서" → "일정 커뮤니케이션이 불명확했다"
- 문제 → 패턴 → 원인 순서로 깊이 파고든다
- 모든 팀원이 최소 1개 이상 발언하도록 유도한다

### Step 4: 액션 아이템 도출

**SMART 기준으로 액션 정의:**
| 기준 | 의미 | 예시 |
|------|------|------|
| **S**pecific | 구체적 행동 | "PR 리뷰 시간 단축" (X) → "PR 오픈 후 24시간 내 리뷰" (O) |
| **M**easurable | 측정 가능 | 완료 여부를 판단할 수 있는 기준 포함 |
| **A**ssignable | 담당자 명시 | 팀 전체 담당 (X) → 개인 또는 소그룹 지정 (O) |
| **R**ealistic | 현실적 | 다음 스프린트 내 실행 가능한 범위 |
| **T**ime-bound | 기한 명시 | 다음 스프린트 내 / 특정 날짜 |

**액션 개수 제한:** 1스프린트당 3개 이하 (집중력 유지)

### Step 5: 이전 회고 액션 점검

```
이전 스프린트 액션 아이템 → 완료 여부 검토 → 미완료 시 원인 파악 → 다시 포함 or 폐기
```

미완료 액션이 반복되면:
1. 액션이 너무 크거나 모호한 것은 아닌가?
2. 담당자가 실제로 리소스를 확보했는가?
3. 팀의 의지가 부족한가, 환경적 장애가 있는가?

| 지표 | 목표 | 실제 |

| 결함 발생 | 2건 이하 | 4건 |
| 팀 에너지 | - | 3.5/5 |

### 회고 의견 (Top 5 투표 결과)

**Liked (좋았던 것)**
- 페어 프로그래밍 도입 후 코드 품질 향상 (5표)
- 데일리 스탠드업 시간 단축 효과 (3표)

**Learned (배운 것)**
- 외부 API 연동 시 Mock 서버 선행 준비의 중요성 (4표)

**Lacked (아쉬웠던 것)**
- QA 단계에서 결함 집중 발견 → 개발 중 테스트 부족 (6표)
- 중간 데모 없이 스프린트 종료 후 피드백 (4표)

**Longed for (바라는 것)**
- 스프린트 중반 미니 데모 도입 (5표)

---

### 액션 아이템
| # | 액션 | 담당자 | 기한 | 성공 기준 |
|---|------|--------|------|---------|
| 1 | PR 오픈 시 단위 테스트 필수 포함 (DoD 추가) | 개발팀 전체 | 다음 스프린트 시작 전 | DoD 문서 업데이트 완료 |
| 2 | 스프린트 D+7일 미니 데모 세션 도입 | 스크럼 마스터 | 다음 스프린트 7일차 | 미니 데모 1회 진행 |
| 3 | 외부 API 연동 스토리에 Mock 태스크 추가 | PO | 다음 플래닝 | Mock 태스크가 백로그에 포함됨 |

### 팀 건강 지수 (1~5)
- 에너지: 3.5 / 협업: 4.0 / 명확성: 3.0 → **전체 평균: 3.5** (전 스프린트 대비 +0.3)

## 품질 기준
- [ ] 스프린트 데이터(포인트, 목표 달성, 결함)가 정량적으로 제시된다
- [ ] 회고 형식이 팀 상황에 맞게 선택된다
- [ ] 액션 아이템이 3개 이하로 집중된다
- [ ] 각 액션에 담당자와 완료 기준이 명시된다
- [ ] 이전 회고 액션의 완료 여부가 점검된다
- [ ] 특정인 비난 없이 시스템/프로세스 관점으로 분석된다
